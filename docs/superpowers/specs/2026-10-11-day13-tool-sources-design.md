# Day 13 第二阶段：工具来源与时间

沿用户已批准的三阶段设计，在第一阶段之后补充来源元数据。当前会话直接执行，不重复申请相同范围的批准。

## 契约

成功工具执行新增可空 `source: ToolSource`，价格列表和计算结果的 `result` 格式保持不变。来源由真实执行器生成，不从模型文字、股票名称或 arguments 接受来源标签。

- `kind` 为 `local_database` 或 `python_calculation`。
- `executed_at` 是后端查询/计算完成的 UTC 时间，带时区，不代表交易日期或上游采集时间。
- `latest_trade_date` 仅为本次返回日线中实际最大的交易日期；无记录、资料查询、计算均为 null。查询区间的 end_date 不代表存在那天的数据，也不代表查询了全库最新记录。
- `record_count` 为日线条数，资料/计算成功为 1；日线为空时为 0，仍然成功并保留 result=[]。
- `upstream_source`、`collected_at` 固定为 null，因为现有库没有保存这些事实。不可声称这些本地记录来自腾讯实时行情。
- `inputs_origin` 仅计算为 `tool_arguments`，其余 null；算式正确不证明模型传入的价格真实。
- 所有失败/拒绝记录 source 为 null，避免伪造成功查询。

`tool_result_messages` 向模型提供相同元数据，继续隐藏私有错误 details；HTTP executions 增加同名 source。系统说明要求来源/交易日标注、空结果不补造、执行时间不等于实时数据、计算输入不能当行情证据。模型仍可能忽略说明，本阶段保证元数据可查，不保证模型自然语言正确。

审计表增加可空 JSON source 列；既有记录为 null，不根据 created_at 倒推来源时间。沿用显式 PostgreSQL schema_upgrade，幂等添加列；不自动修改正式数据库。新建 SQLite 测试库直接使用新模型。已有数据库上线新代码之前须执行升级。

## 验收与边界

内存 SQLite 使用实际资料和日线，覆盖非排序记录、返回区间、空列表、未来查询 end_date、计算和所有错误来源。完整 HTTP → 循环 → 执行器 → 模型反馈 → 审计查询链路中，来源保持一致；未验证客户端历史不能注入 source。既有工具结果和拒绝行为不变。隔离 PostgreSQL 验证旧表升级与记录保留，生产库不用于测试。

第一阶段约束继续有效。建议/执行类型、会话恢复、完整数据供应商追踪、实时 Agent 工具与前端来源展示属于后续工作。分钟行情功能继续保留。

设计自查：执行时间、返回区间最新交易日和采集时间分别定义；没有用计算结果证明输入价格真实性；升级不补造旧审计事实。
