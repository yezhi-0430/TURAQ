# Day 11：工具结果回传与 Agent 循环

用户于 2026-10-09 批准总体方案并审阅本文后授权继续：在现有客户端和工具执行器上增加小型循环，逐段实现与讲解；先完成一次结果回传，再扩展多轮控制。

## 目标与范围

让程序保存对话消息，将工具执行结果回传模型，最终获得文字回答。循环必须区分成功、异常和达到轮数上限。复用三个既有工具、参数校验、白名单及调用日志，不引入 Agent 框架、交易功能或数据库审计表。

第一阶段只验证“模型请求工具 → Python 执行 → 回传结果 → 模型最终回答”。后续阶段增加连续调用、最大轮数及完整终止行为。阶段一完成不代表 Day 11 全部完成。

## 方案选择

采用独立的小型编排函数，复用现有客户端与 execute_tool；消息整理与循环控制分开，便于教学和测试。将循环直接塞进演示命令虽能减少文件，但不便复用和测试；引入 Agent 框架则增加当前阶段不必要的依赖与抽象。

## 消息与模块边界

- 消息顺序为用户问题、包含 tool_calls 的 assistant 消息、各个对应的 tool 消息、下一轮 assistant 响应。
- assistant 消息保留模型提出的调用 ID、名称、原始参数及可空的文本内容；不能只回传计算结果而省略调用请求。
- 每条 tool 消息用 tool_call_id 匹配调用请求，content 为 JSON 字符串。统一结果结构包含成功标志和结果或可公开的错误信息；不将内部异常细节、凭据或日志路径发送给模型。
- 一轮多个调用按顺序经既有执行器处理，全部对应结果追加完成后才发起下一轮请求。有文本且有调用时仍先处理调用。
- 现有消息类型 list[dict[str, str]] 无法表达嵌套 tool_calls 和 null；实现阶段调整工具对话的类型描述，并保持既有纯文本客户端接口兼容。
- 编排函数使用输入消息的独立副本，不修改调用方提供的历史；返回最终状态、可选答案、已请求轮数及工具执行记录。
- 现有 Day 10 单轮入口继续保持单轮语义。离线多轮样例使用可按顺序返回响应的假客户端，不依赖真实服务。

## 循环与终止

每调用一次 chat_with_tools 计一轮；同轮多个工具不增加模型轮数。客户端内部既有连接重试属于传输重试，不另计编排轮数。

1. 有工具调用：先校验并执行，将调用请求及对应结果加入消息历史。
2. 没有工具调用且有非空白文字：成功结束，返回答案。
3. 没有工具调用且文本为 null、空串或纯空白：报告无效模型响应，不标记成功。
4. 工具业务失败或参数失败：沿用执行器拒绝和记录行为，将可公开失败信息回传模型，允许模型在剩余轮数内处理。
5. 模型连接、鉴权、超时或响应解析失败：停止并沿用明确异常，不伪造答案；不增加自动重试循环。
6. max_rounds 默认为 5，必须为正整数且不接受布尔值。达到上限后不能再请求模型。最后一轮如有工具调用，执行并保存结果后返回达到上限状态；如已给出最终回答，则仍成功结束。

达到上限表示未获得最终答案，不把最后一轮“我来计算”等中间文字当作答案。这里的轮数上限不承诺墙钟时间或单轮工具数量上限。

## 第一阶段验收

使用虚构价格 10 和 9，假模型先请求 calculate_change，再返回基于 -10.0000 的文字回答。验证第二次模型请求确实包含原始调用及匹配 ID 的真实执行结果；记录为离线验证，不称作真实千问验收。

第一阶段也验证同轮多个调用的对应关系、工具失败信息可回传、输入历史未被修改。第二次响应若继续请求工具，只保留为待继续状态，不宣称完成；多轮自动处理属于下一阶段。

## 完整验收

- 第一轮直接回答时立即成功，不要求用完轮数。
- 工具调用、回传、最终回答可完成；连续多轮调用可完成。
- 同轮多个工具的消息顺序与 ID 对应正确；文字与调用并存时不提前结束。
- 非法参数仍不进入业务函数，失败可反馈，既有日志保留。
- 无调用且无有效文字被拒绝，模型异常不会被当作成功。
- 持续请求工具最多请求 max_rounds 次，返回未完成状态；上限轮给出答案则成功。
- 非法轮数在发起模型请求或执行工具前被拒绝。
- 使用模拟 HTTP 验证嵌套消息序列化与回传载荷；运行相关测试、全套回归及 Ruff。
