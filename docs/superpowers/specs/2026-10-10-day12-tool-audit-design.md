# Day 12：工具调用数据库审计设计

## 已确认的目标

每次工具调用尝试保存一条记录，成功、参数拒绝、未知工具和执行失败都记录。同一次 Agent 运行使用同一个 run_id，各调用保留模型返回的 tool_call_id。按建表与保存、接入循环、查询验证三个学习阶段推进，每阶段配合讲解与小练习。

## 数据结构

在 app/database.py 中沿用现有 SQLAlchemy 声明方式新增 ToolAuditRecord，表名 tool_audit_records。字段包括：整数主键 id；有索引的 run_id；可空的 tool_call_id；tool_name；原始 arguments 文本；success/error 状态；可空的 JSON result 和 error；非负 duration_ms；带时区的 created_at（UTC，记录保存时间）。参数使用文本保存，因此不合法的 JSON 也能保留。结果中的金额和价格沿用现有字符串表示，避免浮点转换。

run_id 由程序生成 UUID 字符串，不使用模型生成的调用 ID 充当运行 ID。不对 tool_call_id 单独加唯一约束，避免不同运行中的重复 ID 导致记录丢失。数据库约束限制状态和耗时的有效范围。

## 模块与数据流

第一阶段新增 app/audit/repository.py，负责使用独立数据库会话保存已有 ToolExecutionRecord，提交成功才返回。仓储可注入 session factory，便于测试；不提交调用方的业务会话。沿用 Base.metadata.create_all 和现有 schema_upgrade 入口创建新表，不改变既有记录。

第二阶段将审计保存接入工具执行流程：工具执行形成记录后立即保存，保存成功再继续下一次调用或向模型回传。审计写入放在工具业务异常捕获之外，防止保存失败被误报为工具失败。Agent 运行生成一次 run_id，传给各轮及各工具调用，并在运行结果中返回。现有离线入口保留默认不连接数据库的能力；通过明确的审计入口或参数启用持久化，不让既有离线演示隐式依赖生产数据库。

第三阶段提供按 run_id 查询的只读仓储接口和本地演示，按 id 升序返回记录，使用有限条数及游标分页。查询返回空列表表示无记录。当天不新增公开 HTTP 审计接口，内部错误详情不暴露给模型。演示使用虚构数据和假模型，无需真实模型调用。

## 错误和边界

- 校验拒绝也生成并保存 error 记录，错误类型沿用 invalid_arguments。
- 审计数据库写入失败时回滚该独立事务并明确抛出异常，停止后续执行；不自动重试工具，也不声称记录成功保存。
- 已经成功提交的历史记录不因后续模型超时、轮数耗尽或下一次保存失败而回滚。
- 直接回答而没有工具调用的运行产生零条工具审计记录；本阶段不建设完整运行状态表。
- 本设计保证已形成执行记录时尝试持久化，不承诺进程中途崩溃时仍能记录尚未完成的工具调用。
- 不保存 API Key、请求头或完整模型对话；工具参数、结果和内部错误按本地私有运行数据处理。

## 验证与学习验收

第一阶段验证成功记录与失败记录跨会话可读、非法 JSON 参数原样保留、小数结果不丢精度、数据库字段约束、写入失败明确抛错及业务会话不被提交。测试使用隔离测试数据库，并将新表纳入测试清理。

第二阶段验证一轮多个调用和多轮调用共用 run_id、不同运行 ID 不同、失败调用仍落库、直接回答零记录、后续异常保留已写入记录、保存失败阻止后续工具执行。保持既有测试和离线演示兼容。

第三阶段验证查询按运行隔离、稳定排序和分页，再实际运行离线模型配合测试数据库的保存查询演示。运行 pytest 与 Ruff，记录准确结果，不把技术验收等同于用户已能独立编码。

## 方案选择

仅保存散落的调用记录实现最少，但难以还原多轮运行；本方案增加 run_id 来关联，承接 Day 11。完整的建议、确认与模拟成交审计依赖尚未实现的业务，留在对应功能阶段。
